How we build the budgeting app

From a written purpose to a running app/index.html. Humans describe what and why; agents plan, implement, test and ratify each task automatically. Nothing counts as done until an independent tester has checked every acceptance criterion.

Human writes / decides Agent works automatically Quality gate

The pipeline

1
Human · once, then evolves

Describe the purpose

Write purpose.md: who the budgeting software is for, what problem it solves, the core business rules and vocabulary (budget, category, envelope, transaction, period…), and what is explicitly out of scope. Every later step reads this file as its source of truth.

Out: purpose.md
2
Human · per increment

Describe a milestone or a task

A short markdown note in milestones/ saying what the user should be able to do afterwards, e.g. “I can create monthly budgets per category and see what's left.” A small, already-clear change can go in directly as a single task and skip step 3.

In: purpose.mdOut: milestones/M01-*.md
3
Planner agent

Break it into tasks

The planner splits the milestone into small, vertical tasks. Each one yields visible behaviour in the app and has testable acceptance criteria written as Given / When / Then, plus its dependencies on other tasks. If the purpose is ambiguous, the planner asks the human instead of guessing.

In: milestone, purpose.md, existing codeOut: tasks/backlog/NNN-*.md
4
Implementer agent · fully automatic

Implement the task

Pick the next task whose dependencies are ratified and move it to doing/. Write the tests from the acceptance criteria first, then the code, until the tests pass. Tasks run one at a time in the working tree, so the tester always sees exactly one task's change. Each task gets a fresh implementer subagent.

Too big? If the implementer finds a task touches too many areas or won't fit in one focused pass, it splits it into subtasks with their own criteria. Each subtask goes to a separate subagent, and the parent task waits until all of its subtasks are ratified. If the task is unclear rather than big, it goes back to the backlog with a question for the human.
In: task fileOut: code + tests, task → review/
5
Tester agent · fresh context

Verify every requirement

A separate agent that did not write the code. It reads only the task file, the change and purpose.md. It runs the whole test suite, then opens app/index.html in a browser and works through each acceptance criterion like a user would. It writes down a verdict for every criterion, with evidence.

FAIL → the findings go back to step 4 and the implementer fixes them. After 2 failed rounds the task is marked blocked and handed to the human with the full findings.
Out: PASS / FAIL report in the task file
6
Automatic on PASS

Ratify

Move the task to done/, record the test evidence and a one-line changelog entry, and commit. Tasks that depended on this one can now start, and the loop goes back to step 4.

7
Tester agent · per milestone

Milestone acceptance

When every task in a milestone is ratified, the tester runs one end-to-end pass of the milestone's user story against the real page. Then the human tries it out and either closes the milestone or writes the next one.

Out: a working app/index.html

Lifecycle of a task

Who does what

HUMAN

Product owner

Owns purpose.md and milestones. Answers questions and unblocks stuck tasks. Accepts milestones.

AGENT

Planner

Turns a milestone into small vertical tasks with Given/When/Then criteria and dependencies.

AGENT

Implementer

Test-first implementation of one task. Splits it and fans out to subagents when it's too big.

AGENT

Tester

Independent and has fresh context. Runs tests, drives the page in a browser and judges each criterion. It never edits code.

AGENT

Conductor

Runs the loop. The /build skill. Picks the next ready task, dispatches implementer and tester subagents, routes FAIL back, ratifies on PASS.

Definition of done for a task

  • Every acceptance criterion has a PASS verdict from the tester, with evidence.
  • The full test suite is green, so earlier tasks still work.
  • app/index.html opens straight from disk and shows the new behaviour, with no console errors.
  • The language in code and UI matches the vocabulary in purpose.md.
  • The task file is in done/ with its test report, the changelog has its line, and it's committed.

How to run it

  1. Write purpose.md The template's sections are prompts. The skills refuse to plan while the template marker is still in it.
  2. /plan-milestone <what the user should be able to do> or /add-task <one change>. The planner writes the tasks and they're committed.
  3. /build Runs implement → test → ratify until nothing is ready, then runs milestone acceptance.
  4. /status Shows the board and what needs you. Use /unblock <id> <answer> for blocked tasks.
  5. Open app/index.html Try the milestone, then close it or describe what's missing.

Tech decisions

  1. Plain HTML/JS, no build step, no ES modules, so the page runs straight from disk. Domain logic is in app/domain.js and the UI in app/ui.js.
  2. Persistence uses localStorage. Money is stored as integer cents.
  3. Tests use node:test for the domain and Playwright for the acceptance criteria (one test per criterion). The tester also writes its own throwaway probes in .tester/.
  4. Git records one commit per plan and one per ratified task. Nothing is pushed.
